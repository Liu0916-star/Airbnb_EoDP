# model.py 说明

## 一句话

用 11 个特征训练两个模型（KNN 和决策树）来预测一个房源的房东是不是超级房东。先回答"能不能推断出来"，再通过"只给模型看一部分特征"的实验，回答 RQ 的后半句："超级房东身份和**房源基本面**关系更密切，还是和**运营策略**关系更密切？"最后用两种特征选择方法挑出最重要的 3 个特征，并解释两种方法为什么选得不一样。

## 怎么运行

```bash
python3 新代码/model.py
```

- **先运行 `preprocess.py`**，本文件读它生成的 `clean.parquet`（不依赖 `correlation.py`）
- 从哪个目录运行都可以
- 需要 `pandas`、`numpy`、`scikit-learn`、`matplotlib`、`pyarrow`
- 全程大约 **3 分钟**，KNN 最慢。**一定要从头到尾完整运行**（终端里直接 `python3 model.py`），不要在 VS Code 里只跑某一段：之前跑过的变量会一直留在内存里，可能出现用的是旧变量但程序不报错的情况

| | 文件 | 说明 |
|---|---|---|
| 输入 | `data/clean.parquet` | 25,728 行，**全部使用** |
| 输出 | `outputs/evidence_model.json` | 报告 B 部分引用的全部数字 |
| 输出 | `outputs/cv_results.csv` | 调参表，19 行 |
| 输出 | `outputs/rq_experiments.csv` | RQ 实验表，12 行 |
| 输出 | `outputs/feature_ranking.csv` | 11 个特征的各种重要性和排名 |
| 输出 | `outputs/fs_validation.csv` | 只用前 3 个特征的验证结果，6 行 |

| 输出 | `outputs/fig_importance.png` | 置换重要性条形图 |

代码分成 10 段（Section 0–9），每段开头有 `# %%` 标记，对应最终 notebook 的一个 cell。每段内部用 `# ---- 4.3 xxx ----` 这样的小标题再分块。**变量名都用全称**，每行后面有详细注释。

## 背景：读代码前必须知道的五件事

**1. 为什么用全部 25,728 行，不像 correlation 那样只用有评论的**

相关性分析只看两个变量的关系，4,477 个人为填的 4,594 天会扭曲数字，所以去掉。建模要回答的是"给一个房源，能不能猜出它的房东是不是超级房东"，零评论房源也是真实存在的房源，删掉就是只在简单的那部分上考模型；而且删掉会让正类率从 30.65% 变成 35.72%，正是报告里批评 A1 数据集的那种偏差。零评论这件事由 `has_review` 告诉模型。

**2. 11 个特征，分两组**

| 组 | 特征 | 含义 |
|---|---|---|
| 基本面 `fundamentals`（3 个） | `room_type_3`、`dist_cbd`、`accommodates` | 房型、离市中心多远、能住几人：房东基本改不了 |
| 运营策略 `operationals`（8 个） | `availability_365`、`amenity_count`、`days_since_last_review`、`has_review`、`price_num`、`price_missing`、`minimum_nights`、`host_listings_count` | 开放多少天、配多少设施、最近有没有接客、定价、最少住几晚、手上几套房：房东能控制 |

`room_type_3` 是代码里现做的：把合租（Shared room）和酒店（Hotel room）合并成 Other，三类分别是 Entire home/apt 18,829 / Private room 6,616 / Other 283。合并是因为这两类加起来只有 283 行，交叉验证每折只分到几十行，学不出规律。

**白名单写法**：只写要用的 11 列。官方评选标准和由评论推出来的列（`review_scores_*`、`number_of_reviews`、`reviews_per_month`、`number_of_reviews_ltm` 等）没写进来，就自然进不来。不要改成"从 98 列里删掉不要的"，那样漏删一个就会泄漏答案。

**3. 价格用 `price_num`，不用 `price_filled`**

`price_filled` 是用全部 25,728 行的中位数补的，测试集的价格也参与了计算。这里改为在 Pipeline 里只用训练集的中位数来补。

**4. 必须按房东分组切分**

2,730 个多房房东名下有 14,345 个房源，占 55.76%，而同一个房东名下的标签都一样。随机切分的话，同一个房东的房子一部分进训练集、一部分进测试集，模型靠"认出老熟人"就能答对，分数虚高。所以**切测试集、做交叉验证、做 bootstrap 全部按 `host_id` 分组**。

**5. 测试集只考一次**

测试集一开始就锁起来。选超参数、比较特征组合，主要依据都是**训练集上的交叉验证**。测试集用来给正式模型打最终成绩，第 5、7 段的测试分只作为趋势确认。

## 关键概念速查

| 概念 | 一句话 | 在哪段 |
|---|---|---|
| `.fit()` / `.predict()` | fit = 看题目和答案学规律（这就是"机器学习"）；predict = 只看题目交答案 | 第 3 段藏在交叉验证里，第 4 段亲手调用 |
| 分层 + 分组切分 | 两边正类率接近 + 同一房东不跨两边 | 1 |
| Pipeline / ColumnTransformer | 把"补空值 → 编码 → 标准化 → 模型"串成一个整体，fit 时自动只用训练数据算中位数和均值，防止泄漏 | 2 |
| 独热编码 | 房型拆成 3 列 0/1，因为房型之间没有大小 | 2 |
| 标准化 | 每列减均值、除标准差。**只给 KNN 用**：KNN 靠距离，不标准化的话 dsl（最大 4,594）会压倒 has_review（只有 0/1）。决策树只问大于小于，不需要 | 2 |
| 基线 | 永远猜 0。准确率 0.716 看起来不错，macro-F1 只有 0.417，暴露它一个超级房东都找不出来 | 3、4 |
| macro-F1 | 0 类 F1 和 1 类 F1 直接平均，人少的超级房东和人多的非超级房东分量一样 | 3–7 |
| 交叉验证 | 训练集再按房东分 5 份，轮流 4 份训练、1 份打分，取平均 | 3 |
| 超参数 | 训练前由我们定：KNN 的邻居数 k，决策树的最大深度 | 3 |
| 过拟合 / 欠拟合 | k 太小或深度太深 = 背答案；k 太大或深度太浅 = 太笼统 | 3 |
| 混淆矩阵 | 2×2 表：真阴性、误报（FP）、漏掉（FN）、真阳性 | 4 |
| 配对 bootstrap | 按房东有放回抽样 1,000 次，每次同一份样本给两个模型打分，看差值的 95% 区间是否跨过 0 | 4、5 |
| 置换重要性 | 打乱一列，看 macro-F1 掉多少 | 6 |
| Filter / Embedded | Filter：每个特征单独和 y 算关联（MI）；Embedded：模型训练时顺便给出（决策树重要性） | 7 |

## 逐段讲解

### Section 0：数据准备

导入库、找到项目根目录、读 `clean.parquet`、做 `room_type_3`、定义两组特征，取出：
- `X`：11 个特征（题目）
- `y`：答案
- `host_ids`：房东编号，**只用来切分，不进模型**。放进模型的话，它会去记"哪个号码是超级房东"

### Section 1：按房东分组切分

`StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=42)`：分成 5 份，`next()` 只取第一种切法，1 份（约 20%）做测试集，4 份做训练集。

| 键（`evidence["split"]`） | 值 | 说明 |
|---|---|---|
| `train_rows` / `test_rows` | 20,783 / 4,945 | |
| `test_share` | 0.1922 | 房东整体移动，大房东落在哪边比例就偏一点，不会刚好 0.20 |
| `train_hosts` / `test_hosts` | 11,293 / 2,820 | |
| `train_pos_rate` / `test_pos_rate` | 0.3119 / 0.2835 | 差 2.8 个点：大房东大多不是超级房东，落进测试集就把测试集正类率拉低了。**没有换随机种子去挑一个好看的切法**，如实报告 |
| `host_overlap` | **0** | 两边房东的交集，代码里有 assert 检查 |

报告 Methodology 可以直接写：*The group-aware split yielded a 19.2% test set (4,945 listings, 2,820 hosts) with no host overlap; positive rates were 31.2% (train) and 28.4% (test), as whole hosts cannot be divided.*

### Section 2：预处理流水线 + 三个小工具

- **`build_preprocessor(feature_list, scale)`**：造一个预处理器
  - 数字列：补中位数；`scale=True` 时再标准化
  - 房型（名单里有才处理）：独热编码成 3 列
  - 只造不 fit
- **`build_model(model_name, feature_list, hyperparameter)`**：预处理器 + 分类器 = 完整模型。KNN 自动开标准化，决策树不开（切点保留真实单位，好解释）
- **`cross_validate_macro_f1(model, feature_list)`**：在训练集上做 5 折交叉验证（同样按房东分组），返回 5 个 macro-F1

后面所有段落都靠这三个函数，所以同样的 Pipeline 只写了一次。

### Section 3：基线 + 交叉验证调参

每个候选值跑一次 5 折交叉验证，结果存进 `cv_results.csv`：

| KNN 的 k | CV macro-F1 | | 决策树深度 | CV macro-F1 |
|---|---|---|---|---|
| 1 | 0.623 | | 2 | 0.682 |
| 5 | 0.646 | | 3 | 0.687 |
| 11 | 0.654 | | 4 | 0.691 |
| 21 | 0.660 | | **5** | **0.696** |
| 51 | 0.671 | | 6 | 0.688 |
| **101** | **0.675** | | 8 | 0.694 |
| 151 | 0.671 | | 10 | 0.694 |
| 201 | 0.669 | | 15 | 0.675 |
| 301 | 0.671 | | None（不限） | 0.644 |

基线 0.408。

- **KNN 选 k = 101**：k 太小容易被个别邻居带偏，分数一路上升到 101 后开始下降。候选值特意扩到 301，就是为了确认 101 是真正的峰值，而不是正好卡在列表最后一个
- **决策树选深度 5**：不限深度只有 0.644，是典型的过拟合
- **更好的模型是决策树**（`BEST_MODEL_NAME`），只看 CV 选出来，没有看测试集。第 5 段的 bootstrap 和第 8 段的难例都用它

### Section 4：测试集最终评估

**4.1 训练三个正式模型，只考一次**

用最佳超参数，在整个训练集上 `.fit()`，再对测试集 `.predict()`。这里才是训练出"留下来用"的模型；第 3 段训练过的 95 个模型打完分就扔了。

| 模型 | macro-F1 | 准确率 | 1 类 precision | 1 类 recall | 1 类 F1 |
|---|---|---|---|---|---|
| 基线 | 0.417 | 0.716 | 0 | 0 | 0 |
| KNN（k=101） | 0.701 | 0.756 | 0.570 | 0.573 | 0.572 |
| 决策树（深度 5） | **0.721** | 0.777 | 0.613 | 0.581 | 0.596 |

测试分和 CV 分接近（决策树 0.721 vs 0.696），说明选超参数的过程是可信的。测试分略高，和测试集正类率更低（0.2835）有关。

**4.2 混淆矩阵**（`fig_confusion.png`）

| | KNN | 决策树 |
|---|---|---|
| 真阴性（真不是、猜不是） | 2,936 | 3,029 |
| 误报 FP（真不是、猜是） | 607 | 514 |
| 漏掉 FN（真是、猜不是） | 598 | 588 |
| 真阳性（真是、猜是） | 804 | 814 |

两个模型都大约漏掉四成超级房东（1,402 个里漏了 588–598 个），说明有相当一部分超级房东在这 11 个特征上看起来很普通。第 8 段从这些房源里挑难例。

**4.3 配对 bootstrap**

函数 `bootstrap_compare(a 的预测, b 的预测)`：从 2,820 个测试房东里**有放回**地抽 2,820 个，拼出他们的全部房源，在这份样本上同时给 a 和 b 打分，重复 1,000 次，取中间 95% 的范围。**按房东抽不按房源抽**，理由和分组切分一样。

KNN（a）对决策树（b）：

| | 95% 区间 |
|---|---|
| KNN | [0.676, 0.722] |
| 决策树 | [0.693, 0.749] |
| 决策树 − KNN | **[−0.002, 0.046]**：跨过 0 |

**写报告时只能说"决策树略高，但差距在统计上不显著"，不能说"决策树更好"。**

### Section 5：RQ 实验

只给模型看一部分特征，看它还能考多少分。超参数沿用第 3 段，不重新调（报告写一句 *hyperparameters fixed at values tuned on the full feature set*）。

| 组 | 特征 | 数量 | DT CV | KNN CV | DT 测试 | 回答什么 |
|---|---|---|---|---|---|---|
| A | 只用基本面 | 3 | 0.485 | 0.495 | 0.500 | RQ 后半句 |
| B | 只用运营 | 8 | **0.701** | 0.676 | 0.727 | RQ 后半句 |
| C | 全部 | 11 | 0.696 | 0.675 | 0.721 | 对照组，代码里自检它和第 4 段完全一样 |
| D | 全部去掉 dsl + has_review | 9 | 0.672 | 0.656 | 0.680 | 是不是全靠评论新近度？ |
| E | 全部去掉 availability_365 | 10 | 0.698 | 0.667 | 0.724 | 填报告的 [TO BE CONFIRMED] |
| F | 只用运营，去掉 dsl + has_review | 6 | 0.670 | 0.652 | 0.681 | 最关键的稳健性检查 |

dsl 和 has_review **一起去掉**：has_review 就是在说明 dsl 是不是填出来的，只去掉一个没有意义。

配对 bootstrap（用决策树）：

| 比较 | 差值 95% 区间 | 结论 |
|---|---|---|
| B 运营 − A 基本面 | **[0.184, 0.266]** | 不跨 0，运营组显著更强 |
| F 运营去评论 − A 基本面 | **[0.130, 0.231]** | 去掉评论特征后仍然显著更强 |

怎么读：
- **只用基本面，只比基线（0.41）高一点**；只用运营，和 11 个全用一样好，甚至略高。基本面几乎没有额外贡献
- **F 组是结论稳不稳的关键**：如果运营组的优势全靠评论新近度（它部分代表评论活跃度，是被剔除指标的近亲），F 会掉到和 A 差不多。实际上 F 仍有 0.670，所以结论站得住
- **D 组**：去掉评论那一对，决策树掉了约 0.025，评论新近度有贡献，但不是全部
- **E 组**：去掉 availability_365，决策树几乎不变（0.698 vs 0.696），KNN 掉 0.008。**它可有可无**，原因见第 7 段：它的信息和 dsl 重叠

**报告措辞**：运营组 8 个特征、基本面组只有 3 个，特征多信息自然多，这是一个不公平之处。所以要写 *operational features **as a set** were more closely associated with superhost status*，并在 Limitations 里承认数量不对等。F 组（6 个）也部分回应了这个问题。全程用"associated with"，不能写"driven by / caused by"。

### Section 6：特征影响力

三种重要性放在一张表里（`feature_ranking.csv`）：

| 特征 | 组 | 决策树自带 | 决策树置换 | KNN 置换 |
|---|---|---|---|---|
| days_since_last_review | 运营 | **0.742** | **0.137** | 0.043 |
| host_listings_count | 运营 | 0.125 | 0.031 | 0.011 |
| amenity_count | 运营 | 0.102 | 0.082 | **0.087** |
| dist_cbd | 基本面 | 0.010 | 0.003 | 0.013 |
| minimum_nights | 运营 | 0.009 | 0.002 | 0.003 |
| availability_365 | 运营 | 0.008 | 0 | 0.031 |
| price_num | 运营 | 0.004 | 0 | 0.008 |
| price_missing | 运营 | 0 | 0 | 0.036 |
| has_review | 运营 | 0 | 0 | 0.001 |
| room_type_3 | 基本面 | 0 | 0 | 0.005 |
| accommodates | 基本面 | 0 | 0 | 0.002 |

- **决策树自带重要性**（`feature_importances_`）：每个特征在所有切分里贡献的纯度提升之和，总和为 1。房型被独热编码成 3 列，代码里把它们加回 1 个。缺点：在训练集上算；偏爱可切位置多的连续特征
- **置换重要性**（`permutation_importance`）：在测试集上把一列打乱 10 次，看 macro-F1 平均掉多少。两个模型都能用，所以决策树也算了一次，两个模型用同一把尺子比较。很小的负数等于没用
- **相关特征会互相掩护**：打乱 dsl 时 has_review 还在，模型能从它那里拿到一部分信息，所以两者看起来都没那么重要

怎么读：
- 三列的前三名几乎全是运营特征，和第 5 段互相印证
- 决策树极度依赖 dsl（自带重要性 0.74），深度 5 的树第一刀很可能就切在它上面
- **KNN 和决策树用的特征不一样**：KNN 最依赖 amenity_count，而且 price_missing、availability_365 对它也有用，决策树却完全不用这两个。这是因为决策树用 dsl 切完以后，这两个特征已经没有新信息了（price_missing ≈ 下架 ≈ 很久没评论）；KNN 是把所有特征一起算距离，没有"先用谁"的概念

### Section 7：特征选择

**两种方法**

| | Filter（过滤法） | Embedded（嵌入法） |
|---|---|---|
| 做法 | `mutual_info_classif`：每个特征**单独**和 y 算互信息 | 直接用第 6 段的决策树自带重要性 |
| 看的是 | 这个特征自己和 y 的关联有多强 | 这个特征在模型里有多少**额外**贡献 |
| 只用训练集 | ✓ | ✓（树是在训练集上训练的） |

这里的 MI 是 sklearn 直接估计连续值的版本，和 correlation.py 里先分箱再算的 MI **数字不能互相比较**。

**结果**

| | 前 3 |
|---|---|
| Filter | days_since_last_review、host_listings_count、**availability_365** |
| Embedded | days_since_last_review、host_listings_count、**amenity_count** |
| 两者都选中 | days_since_last_review、host_listings_count |

**只用前 3 个特征重新打分**（`fs_validation.csv`）：

| 特征 | DT CV | DT 测试 | KNN CV |
|---|---|---|---|
| Filter 前 3 | 0.666 | 0.685 | 0.672 |
| **Embedded 前 3** | **0.702** | **0.729** | 0.670 |
| 全部 11 个 | 0.696 | 0.721 | 0.675 |

**这就是报告 Feature Selection Interpretation（2 分）要写的内容：**

1. **Filter 高、Embedded 低 → 信息重复**：availability_365 单独看和 y 的关联很强（MI 排第 3），但它和 dsl 携带的信息高度重叠（correlation 那张表里 DSLR ~ AV365 是关联最强的一对，NMI 0.0856）。树先用 dsl 切了，availability 就没有新东西可贡献了，Embedded 排名掉到第 6。has_review 也一样：MI 0.035，在树里的重要性是 0
2. **Embedded 选了补充新信息的 amenity_count**，所以只用 3 个特征就和 11 个全用一样好（0.702 vs 0.696）；Filter 浪费了一个名额在重复信息上，只有 0.666。这是 Filter "忽略特征之间重复"的实际代价
3. **反过来的情况**：dist_cbd 的 Embedded 排名（第 4）高于 Filter 排名（第 7），但置换重要性很低。这是决策树偏爱连续特征的表现（可切位置多），不代表它真的有用
4. **对 RQ**：两种方法选出的前 3 名全部是运营特征

### Section 8：难例分析

从决策树漏掉的 588 个超级房东里，挑模型**最有把握**判错的那一个（`predict_proba` 给出的"是超级房东"的概率最低）。

**房源 46835268**（房东 349701），模型认为它是超级房东的概率只有 **0.0014**：

| 特征 | 这个房源 | 超级房东中位数 | 非超级房东中位数 | 更像 |
|---|---|---|---|---|
| days_since_last_review | **813** | 37 | 503.5 | 非超级 |
| dist_cbd（km） | 27.2 | 4.41 | 5.01 | 都不像，偏远 |
| availability_365 | 77 | 195 | 106 | 非超级 |
| amenity_count | 42 | 45 | 31 | 超级 |
| host_listings_count | 1 | 3 | 2 | 非超级 |
| price_num | 264 | 255 | 234 | 超级 |

背景（被排除的列，只用来解释，不当特征）：这个房东只有这一套房，房源一共有 12 条评论，最后一条在 813 天前。

**怎么写**：它看起来是一个两年多没有人入住、几乎已经不活跃的房源，标签却还是超级房东。模型根据"最近有没有在接客"判断它不是，从特征上看判得合理。可能的解释是**标签反映的时间段和特征反映的时间段不一致**，比如称号是早年活跃时拿到的，数据快照里还没更新。这只是推测，数据里无法验证，报告里用 *may* 这类说法。这是房源级快照建模的结构性局限：任何只看当前房源特征的模型都会漏掉这类情况。

## 常见疑问

**为什么 KNN 要标准化，决策树不用？**
KNN 用距离判断"像不像"，数字大的特征会主导距离。决策树每次只看一个特征问"大于还是小于"，数字整体放大缩小，答案不变；不标准化还能让切点保留真实单位，好解释。

**为什么超参数用交叉验证选，不直接用测试集选？**
用测试集选，就等于考前偷看了考卷，最后的测试成绩不再可信。

**第 5、7 段也用了测试集，不是说只考一次吗？**
这两段的结论主要依据 CV 分数，测试分只用来确认趋势；超参数也没有根据测试结果再调整。报告里比较特征组合时引用 CV 分数。

**测试分为什么比 CV 分高一点？**
测试集正类率（28.35%）比训练集（31.19%）低，而且 CV 每折只用 4/5 的训练数据训练，正式模型用了全部训练数据。

**置换重要性出现很小的负数是 bug 吗？**
不是。打乱后分数碰巧略高一点，意思就是这个特征没用，当 0 看。

**为什么第 8 段用决策树，不用 KNN？**
代码自动用第 3 段 CV 更好的那个模型（`BEST_MODEL_NAME`），这次是决策树。

**能不能把特征选择换成 PCA？**
不能。特征选择是从原始特征里挑子集，挑出来的还是原来的列，能说清楚是"基本面"还是"运营"；PCA 把所有特征混合成新特征，没法回答 RQ。PCA 是 C 板块的内容。
