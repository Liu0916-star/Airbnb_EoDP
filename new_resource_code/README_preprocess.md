# preprocess.py 说明

## 一句话

把 Inside Airbnb 的原始房源数据清洗成一张干净的表 `clean.parquet`，**全组后面所有分析都只读这张表**；同时把报告预处理部分要引用的数字存进 `evidence.json`。

## 怎么运行

```bash
python3 新代码/preprocess.py
```

- 从哪个目录运行都可以，代码会自己找到项目根目录
- 需要 `pandas`、`numpy`、`pyarrow`（保存 parquet 用）
- **必须第一个运行**，`correlation.py` 和 B、C 板块都依赖它的输出

| | 文件 | 说明 |
|---|---|---|
| 输入 | `data/listings.csv` | Inside Airbnb 墨尔本原始数据，25,728 行 × 90 列 |
| 输出 | `data/clean.parquet` | 25,728 行 × 98 列（原始 90 列 + 新增 8 列） |
| 输出 | `outputs/evidence.json` | 报告预处理部分引用的全部数字 |

代码分成 8 段，每段开头有 `# %%` 标记。VS Code 里可以一段一段单独运行；最后交的 notebook 也是一段对应一个 cell。

## 背景：读代码前必须知道的四件事

**1. 我们在研究什么**

RQ：*Can superhost status be inferred from listing attributes and host operating behaviour once Airbnb's own criteria are excluded, and is it more closely associated with listing fundamentals or operational strategy?*

超级房东是 Airbnb 按规则评出来的，规则里有评分、近一年入住次数等。如果把评分、评论数直接给模型，模型只是在背 Airbnb 的规则，没有意义。所以我们**把这类官方指标剔除**，看剩下的房源属性和房东行为还能不能推断出超级房东，以及更接近哪一边：

- **房源硬实力**：区位、户型等，房东改不了
- **运营策略**：在架天数、设施投入、最近有没有在接客等，房东能控制

**2. 目标变量是房东级的**

`host_is_superhost` 是给**房东**的称号，同一个房东名下所有房源的标签完全相同（第 7 段的检查 2 会确认这一点）。而 2,730 个多房房东名下有 14,345 个房源，占全部的 55.76%。所以 **B 板块建模时必须按 `host_id` 分组切分训练集和测试集**，否则同一个房东会同时出现在两边，模型等于提前看到了答案。

**3. 数据源换过一次**

课程 Amendment #1 要求只能用 Inside Airbnb 原始数据，禁止用 A1 的数据集。A1 数据集其实是原始数据删掉了全部 4,477 个零评论房源，而这批房源的超级房东率只有 6.59%（其余是 35.72%），所以 A1 数据有偏差。**本文件不删任何行**，零评论房源全部保留并单独处理（见第 2 段）。

**4. 这个文件刻意不做的三件事**

| 不做 | 原因 |
|---|---|
| 标准化（缩放到同一尺度） | 标准化要用平均值和标准差，在这里算就用上了测试集的数据。要到建模时只用训练集算 |
| 切分训练集和测试集 | 建模的事，而且必须按房东分组 |
| 删除任何行 | 零评论、缺价格的房源超级房东率都明显偏低，删掉会让数据偏向超级房东 |

## 逐段讲解

### 第 0 段：准备

- `PROJECT_ROOT`：项目根目录。本文件放在 `新代码/` 里，往上一层就是根目录，`data/` 和 `outputs/` 都从这里拼出来。这样无论终端当前在哪个位置，都能找到文件
- `round_value(value, digits)`：小工具，把数字转成普通小数并保留 `digits` 位。pandas 算出来的是 numpy 类型，直接存 json 会报错
- `listings`：整张房源表，一行 = 一个房源
- `evidence`：一个字典，叫**记账本**。后面每算出一个报告要用的数字，就往里记一笔，最后整个存成 `evidence.json`。**写报告时预处理的数字一律从这里抄**，保证报告和代码一致

代码里的变量名都用全称（比如 `has_review_mask`、`price_is_missing`、`is_unavailable_all_year`），看名字就知道是什么；每行后面还有详细注释。

### 第 1 段：解析，把文字变成数字

原始数据里价格、设施都是文字，模型不认，要先转成数字。做法沿用 A1。

**价格 `price_num`**

`"$1,306.99"` → 删掉 `$` 和逗号 → `1306.99`。空的仍然是空。

必须整串转换，不能用正则去"找一段数字"：遇到千位逗号会只抓到 `306.99`，这是 A1 里修过的 bug。

**设施个数 `amenity_count`**

`amenities` 长这样：`'["Wifi", "Kitchen", "HDTV with Chromecast, DVD player"]'`。看起来是列表，其实是一串文字。用 `json.loads` 解析成真正的列表再数个数，结果是 **3**。

不能直接按逗号切：第三项名字里有个逗号，按逗号切会数成 4。

**目标 `y`**

`host_is_superhost` 原本是 `"t"` / `"f"`，转成 1 / 0。整体超级房东率 30.65%。

**一个房东多套房：B 板块为什么必须按房东分组**

先数每个房东名下有几套房：

| 键 | 值 | 含义 |
|---|---|---|
| `single_listing_hosts` | 11,383 | 只有 1 套房的房东 |
| `multi_listing_hosts` | 2,730 | 有 2 套以上的房东 |
| `multi_listing_listings` | 14,345 | 这 2,730 个房东名下的房源总数 |
| `multi_listing_share` | 55.76% | 占全部房源的比例 |

也就是说，**超过一半的房源和别的房源同属一个房东**。再加上同一个房东名下的标签都一样（下面的例子），随机切分就会出问题。

同一个房东名下的标签是否都一样，例子：

| 房东 | 名下房源 | 每套的 y | 名下有几种不同的 y |
|---|---|---|---|
| 甲 | A、B、C | 1、1、1 | 1 种 |
| 乙 | D、E | 0、0 | 1 种 |
| 丙（假设） | F、G | 1、0 | 2 种 |

代码按房东分组，数每个房东名下有几种不同的 `y`，再取所有房东里的最大值。如果存在丙这样的房东，结果会是 2。**实际结果是 1**：同一个房东名下的房源，要么全是 1，要么全是 0。原因是超级房东是给房东本人的称号，不是给某套房子的。

**为什么要检查**：它决定了 B 板块怎么分训练集和测试集。如果随机分，甲的 A、B 进训练集、C 进测试集，模型在训练时已经见过"甲的房子是超级房东"，考 C 时认出是同一个房东（很多特征完全一样，比如房东房源数）就能直接答对，分数虚高。所以**必须按 `host_id` 分组**，同一个房东的房源全部在训练集或全部在测试集。

### 第 2 段：步骤 1 —— 距上次评论天数 + 零评论房源

**这个特征是什么**

评论只有在有人住过之后才会出现，所以"最后一次评论距今多少天"可以粗略代表**这个房源最近有没有在接客**。天数越小越活跃。它属于**运营策略**一侧。

**怎么算**

```
天数 = 参考日 − 这个房源的最后评论日期
```

**参考日 = 整个数据集中最晚的那条评论日期 = 2026-06-28。** 不用今天的日期，因为数据是某一天抓取的快照，最晚的评论日期大约就是抓取日；如果用今天，今天跑和下个月跑，所有天数会整体差 30 天，结果不能复现。

**零评论房源怎么办（这一步报告的得分点）**

有 **4,477 个房源（17.4%）从来没有评论**，它们的天数算不出来，是空的。模型不接受空值，必须处理。三个选项：

| 做法 | 结论 |
|---|---|
| 删掉这 4,477 行 | ❌ 它们的超级房东率只有 6.59%，其余是 35.72%。删掉后正类率会被推高，就是 A1 数据集的问题 |
| 填中位数 84 天 | ❌ 84 天意思是"最近挺活跃"，而这些房源根本没人住过，意思反了 |
| **填 4,594 + 新增 `has_review` 列** | ✅ 采用。4,594 = 最大天数 4,593 + 1，意思是"比最久没评论的还要久"；`has_review` 再单独告诉模型"这条从来没有评论" |

注意 `has_review` 必须**在填充之前**造：填完之后就分不出哪些原本是空的了。

**记账的数字**

| 键 | 值 | 用途 |
|---|---|---|
| `dsl_median` | 84 | 有评论房源的天数中位数 |
| `dsl_mean_super` / `dsl_mean_nonsuper` | 93.10 / 727.03 | 超级房东明显更活跃（均值口径，受少数极大值影响） |
| `no_review_n` / `no_review_pct` | 4,477 / 17.4% | 零评论房源规模 |
| `superhost_rate_no_review` / `_has_review` | 6.59% / 35.72% | 不能删行的理由 |
| `superhost_n_in_no_review` | 295 | 零评论房源里仍有 295 个超级房东 |
| `superhost_n_in_no_review_host_reviewed` | 271 | 其中 271 个的房东另有有评论的房源 |
| `dsl_vs_reviews_ltm_spearman` | −0.8155 | 见下方"要承认的问题" |
| `dsl_fill_value` | 4,594 | 填充值 |

平均值和中位数都**只在有评论的房源上算**，不然 4,477 个 4,594 会把平均值拉得很高。

**要在报告里承认的问题**

- `has_review` 其实就等于"评论数 > 0"，而评论数是我们说要剔除的官方指标。辩护：官方门槛比"有没有过任何一条评论"严格得多；而且零评论房源里还有 295 个超级房东，说明它不是标签的替身
- `days_since_last_review` 和"近 12 个月评论数"的相关系数是 −0.8155，关系很强：近一年评论多的房源，最后一条评论自然离现在近。所以这个特征**部分代替了评论数**。这一条写进 Limitations。B 板块已经做了"有 / 没有这两个特征"的对比（model.py 第 5 段 D、F 组）：全部特征去掉这两个后，决策树 CV macro-F1 从 0.696 降到 0.672；只用运营特征去掉这两个后仍有 0.670，远高于只用基本面的 0.485

**给下游的提醒**

4,477 个 4,594 全堆在同一个值上。做相关性、PCA、聚类时，这堆人为的值会被当成真实结构。所以**这类分析请只用 `has_review == 1` 的 21,251 行**，`correlation.py` 就是这么做的。建模时可以用全部行，配合 `has_review` 一起用。

### 第 3 段：步骤 2 —— 设施个数

设施个数第 1 段已经算好了，这里做两件事。

**1. 证明这一步确实修正了东西（before / after）**

模板要求每个预处理步骤都要给出"做之前 vs 做之后"的具体数字。所以这里用 A1 里那个**错误的数法**（去掉方括号后按逗号切）再数一遍，和正确结果比较：

- **3,096 行（12.03%）会被数错**
- 单个房源最多差 **21 项**

这就是报告里步骤 2 的 before / after。

另外，29 个房源（0.11%）一项设施都没有，是真实的空列表，不是解析出错。

**2. 看这个特征有没有区分度**

超级房东平均 **44.08** 项设施，非超级房东 **31.03** 项。

**归类**：设施算**运营策略**，因为房东随时可以增减，而位置和户型改不了。

### 第 4 段：步骤 3 —— 价格缺失

价格缺了 **6,553 个（25.47%）**。这一段回答三个问题：为什么缺、能不能删、怎么补。

**为什么缺：三个条件概率**

`availability_365 == 0` 表示全年可订 0 天，也就是**下架**了。

| 键 | 值 | 大白话 |
|---|---|---|
| `p_miss_given_av0` | 0.9985 | 下架的房源里，99.85% 没有价格 |
| `p_miss_given_avpos` | 0.0222 | 在售的房源里，只有 2.22% 没有价格 |
| `p_av0_given_miss` | 0.9335 | 没有价格的房源里，93.35% 是下架的 |

前两个一起看：**缺不缺价格几乎完全取决于有没有下架**，不是随机缺的。第三个是反过来问的，分子分母都换了，**写报告时别和第一个搞混**。

**能不能删：不能**

下架房源的超级房东率 8.13%，在售的 37.68%。删掉缺价格的行，几乎等于删掉所有下架房源，数据就偏了。

**怎么补**

- `price_filled`：缺的全部补成**所有房源价格的中位数 $243.67**。用中位数不用平均数，因为有一晚几万的极端价格，平均数会被拉高
- `price_missing`：标记这条原本缺价格。模型看到它，就知道这里的 243.67 是补的，而且这条大概率下架了
- `price_num`：原样保留带空值的版本

**那 10 次抽样在干什么**

B 板块会把数据分成训练集和测试集。严格来说，补价格用的中位数应该**只用训练集**算，而这里用了全部数据，测试集房源的价格也参与了计算，算是轻微的"偷看"。

为了证明影响可以忽略：随机抽 75% 的房源（大约是训练集的大小）算中位数，重复 10 次，结果都在 **$243.0 到 $245.0** 之间，和全量的 $243.67 相差不到 1%。

**B 板块的做法**：model.py 建模时用的是 `price_num` 加 `price_missing`，在 `Pipeline` 里用 `SimpleImputer` 只拿训练集的中位数来补，这个问题在建模里已经彻底没有了。`price_filled` 留给不需要切分训练 / 测试集的分析（比如 C 板块的聚类）使用。

### 第 5 段：到市中心的距离

不算三个受评步骤，但相关性分析和建模都要用。

- **原点**：Flinders Street 火车站（纬度 −37.8183，经度 144.9671）。市中心是一片区域不是一个点，选它是因为它是墨尔本最主要的交通枢纽，**报告里要说明这个选择**
- **南北方向**：纬度差 × 111 公里
- **东西方向**：经度差 × 111 × cos(纬度)。地球是球形，越往南北极经线越密，在墨尔本经度差 1 度只有约 88 公里。`np.cos` 只认弧度，所以要先 `np.radians`
- 两个方向用勾股定理合成直线距离

这是平面近似，墨尔本的房源分布范围不大，误差可以忽略。

距离属于**房源硬实力**，房东改不了。

### 第 6 段：三个弃用候选步骤的证据

模板要求：列出 6 个候选预处理步骤，只做 3 个，并**用数据集里的真实数字**说明为什么不做另外 3 个。这一段只算这些数字，**不修改任何数据**。

| 做了 | 没做 |
|---|---|
| 步骤 1：距上次评论天数 | 补 bedrooms / beds 缺失值 |
| 步骤 2：设施个数 | 合并 property_type 类别 |
| 步骤 3：价格缺失处理 | minimum_nights 分成短租 / 长租 |

**不补 bedrooms**

卧室数缺了 18.19%（床数缺 27.44%）。但按房型拆开：整套房只缺 2.47%，单间缺 61.28%，差约 25 倍。租单间时"这套房子有几个卧室"不重要，房东就不填。缺失本身有含义，硬补一个数是造假。房子能住几个人已经由 `accommodates` 这一列表示。

**不合并 property_type**

房源类型有 82 种，其中 41 种不到 10 个房源。但这 41 种加起来只有 **111 行（0.43%）**，合并最多影响 0.43% 的数据。另外整套房占全部房源 73.18%，每种房型里最多的那一种类型在四类中三类占一半以上，主要信息已经被 `room_type` 覆盖。

**不给 minimum_nights 分档**

最少要住 30 晚以上的房源只有 **426 个（1.66%）**，分出来的长租组太小，模型学不到东西。

### 第 7 段：检查并保存

三条检查，不成立就报错停下：
1. 行数没变（确认没删行）
2. 同一房东名下标签一致（每个房东名下不同 `y` 值最多 1 种）。这是内部检查，结果不写进报告，报告里用上面的多房房东数字说明为什么要分组
3. 天数和价格填充后没有空值

然后保存 `clean.parquet` 和 `evidence.json`，并把记账本打印出来方便核对。

## 给后面板块的使用须知

1. **只从 `data/clean.parquet` 读数据**，不要自己重新清洗 `listings.csv`。全组数字一致全靠这一点
2. **目标是 `y`**，不是 `host_is_superhost`
3. **按 `host_id` 分组切分**训练集和测试集
4. **建模时要剔除的列**：原本剔除的 5 个官方指标（`review_scores_rating`、`review_scores_cleanliness`、`review_scores_value`、`number_of_reviews`、`reviews_per_month`），加上原始数据里同类的列：`review_scores_accuracy` / `_checkin` / `_communication` / `_location`、`number_of_reviews_ltm` / `_l30d` / `_ly`、`estimated_occupancy_l365d`、`estimated_revenue_l365d`（后两个是 Inside Airbnb 用评论数估算出来的）
5. **`days_since_last_review`**：相关性 / PCA / 聚类只用 `has_review == 1` 的行；建模时和 `has_review` 一起用
6. **价格**：建模优先用 `price_num` + `price_missing`，在训练流程里补缺失；`price_filled` 是已经用全量中位数补好的版本

## 常见疑问

**为什么不删零评论房源，它们不就是没用的数据吗？**
它们的超级房东率只有 6.59%，删掉会让整体超级房东率从 30.65% 变成 35.72%，模型学到的是一个偏向超级房东的世界。

**`has_review` 是不是违反了 RQ？**
它是评论数的粗化版本，有张力，所以要在报告里承认。但它只区分"有没有过任何评论"，远比官方门槛粗；零评论房源里还有 295 个超级房东。B 板块的对比实验（model.py 第 5 段）显示，去掉它和 dsl 后结论不变。

**为什么用中位数补价格，不用平均数？**
价格有极端值，平均数会被拉高，中位数不受影响。
